# Field Incident Reporter — Spec

Status: ready-for-agent

Vocabulary follows [GLOSSARY.md](../../GLOSSARY.md). Decisions and their reasons live in [docs/adr/](../../docs/adr/); this spec states *what* to build and links the ADR for *why*.

## Goal

A prototype facility-maintenance system:

- **Technicians** use an Android app to report incidents with photos, view the incidents they reported, and edit or withdraw them while they are Open. The app works offline.
- **Operators** use a Next.js web dashboard to triage, filter, manage and resolve every incident.
- A **local json-server** is the backend for both.

The Android app is the main focus of the project; it gets the most rigour. The server and dashboard only need to be correct and tidy.

## Out of scope (v1)

- Real security: plain-text passwords, tokens that never expire, no HTTPS.
- An incident history or audit trail.
- Video, voice notes and attachments other than photos.
- Anonymous reporting.
- Push or system notifications, and realtime updates on the dashboard.
- Technicians seeing assignees or notes.
- Search or filters on Android.
- Zooming or full-screen photo viewing.
- Bulk actions, charts and a full-map view on the dashboard.
- Compose UI tests and dashboard end-to-end tests.

## Repository layout


## 1. Server (`server/`)

See [ADR-0001](../../docs/adr/0001-json-server-behind-custom-server-js.md).

### Scripts
- `npm run dev` starts `server.js` on port 3001.
- `npm run reset` copies `seed.json` over `db.json` and deletes non-seed files in `uploads/`. Because the copy also overwrites `sessions`, every token is invalidated.

### Collections (`db.json`)

All ids are opaque strings, generated by `server.js`. All timestamps are epoch milliseconds (numbers).

```jsonc
users:      { id, email, password, name, role: "technician" | "operator" }
sessions:   { id /* = token */, userId, createdAt }
categories: { id, name }
severities: { id, name, rank /* 1 = Low … 4 = Critical */ }
sites:      { id, name, lat, lng }
incidents: {
  id, reporterId,
  title, description, categoryId, severityId, siteId,
  locationDescription,                               // string, may be ""
  position: { lat, lng, accuracyM } | null,
  photoUrls: string[],                               // relative, e.g. "/uploads/ab12.jpg"; 1–3
  status: "open" | "acknowledged" | "in_progress" | "resolved" | "rejected" | "withdrawn",
  priority: "low" | "medium" | "high" | "urgent" | null,
  assignee: string | null,
  notes: [{ at, byUserId, text }],
  createdAt,   // set by the device when the technician first saves; never changes
  receivedAt,  // set by the server on first insert
  updatedAt    // set by the server on every write
}
```

### Seed
- **Users:** `tech1@example.com` and `tech2@example.com` (technicians) and `ops@example.com` (operator). Every password is `password`.
- **Sites:** North Plant, Depot A and HQ Campus, each with real-looking coordinates.
- **Categories:** Equipment, Electrical, Plumbing, HVAC, Structural, Road/Grounds Hazard, Other.
- **Severities:** Low (1), Medium (2), High (3), Critical (4).
- **Incidents:** about 8, spread across both technicians and covering every status. Seed photos go in `uploads/seed/`.

### Auth
- `POST /login` with `{ email, password }`:
  - Success: **200** `{ token, user: { id, email, name, role } }`, and a new `sessions` row is created.
  - Bad credentials: **401**.
- `POST /logout` returns **204** and deletes the caller's session.
- Every other route except `GET /uploads/*` needs `Authorization: Bearer <token>`. A missing or unknown token gets **401**.

### Error body
Every 4xx response carries `{ "error": "<message>", "fields"?: { "<field>": "<message>" } }`.

### Catalog (any role)
`GET /categories`, `GET /severities`, `GET /sites`.

### Technician routes
| Route | Behaviour |
|---|---|
| `GET /incidents/summary` | The caller's incidents, excluding `withdrawn`, newest `createdAt` first. Each item is `{ id, title, categoryId, severityId, status, createdAt, updatedAt }`. |
| `GET /incidents/:id` | The full incident with **`assignee` and `notes` removed**. **404** if it doesn't exist or isn't the caller's. |
| `POST /incidents` | Body: `{ title, description, categoryId, severityId, siteId, locationDescription, position, photoUrls, createdAt }`. The server sets `reporterId` from the token, plus `status: "open"`, `priority: null`, `assignee: null`, `notes: []`, `receivedAt` and `updatedAt`. **Dedupe** ([ADR-0003](../../docs/adr/0003-create-dedupe-by-reporter-and-created-at.md)): if an incident already has the same `reporterId` and `createdAt`, the server updates its report fields instead of inserting. **Both cases return 200** with the incident (technician view). **400** if validation fails. |
| `PATCH /incidents/:id` | Accepts either a subset of the report fields (no `createdAt`) or exactly `{ status: "withdrawn" }`. **409** if the current status isn't `open`. **400** if any other field is present. **404** if the incident isn't the caller's. Returns 200 with the incident (technician view). |

Validation, applied to POST and to PATCH for the fields present:
- `title`: 1–80 chars.
- `description`: up to 1000 chars.
- `categoryId`, `severityId`, `siteId`: must exist.
- `photoUrls`: 1–3 entries.

### Operator routes
| Route | Behaviour |
|---|---|
| `GET /incidents` | All incidents, full. Supports standard json-server 0.17 filtering (`status=`, `severityId=`, …), `q=`, `_sort`/`_order`, `_page`/`_limit` and the `X-Total-Count` header. Also accepts `createdAt_gte`/`createdAt_lte`. |
| `GET /incidents/:id` | The full incident. |
| `PATCH /incidents/:id` | Body: any of `{ status, priority, assignee, note }`. `note` is a string, and the server appends `{ at, byUserId, text }` to `notes`. **409** on a status change not in the transition table below, or on any change to a `resolved`, `rejected` or `withdrawn` incident. **400** on any other field. |
| `GET /users` | Users without `password`, so the dashboard can show reporter names. |

Status transitions an operator may make:

```
open         → acknowledged | rejected
acknowledged → in_progress  | rejected
in_progress  → resolved     | rejected
```

### Everyone
- `DELETE` on any route returns **405** ([ADR-0005](../../docs/adr/0005-withdraw-instead-of-delete.md)).
- A technician calling an operator-only route, or the reverse, gets **403**.

### Uploads
- `POST /uploads`: multipart with field `file`. Allowed types are `image/jpeg`, `image/png` and `image/webp`, up to 15 MB. The file is stored as `uploads/<random>.<ext>`. Returns **201** `{ url: "/uploads/<random>.<ext>" }`.
- `GET /uploads/*` is served statically **without auth**.

## 2. Dashboard (`dashboard/`)

- Next.js App Router, TypeScript, Tailwind and shadcn/ui.
- **Data flow:** Server Components fetch from `http://localhost:3001`. Server Actions perform mutations and call `revalidatePath`. There is no client-side data library and no realtime.
- **Auth:**
  - The `/login` page posts to the server's `/login`.
  - Any account whose role isn't `operator` is rejected with "Operators only".
  - The token is stored in an **httpOnly cookie**.
  - `middleware.ts` redirects to `/login` when the cookie is missing, and a 401 from the server clears the cookie and redirects there too.
  - Logout calls `/logout` and clears the cookie.
- **`/incidents` (table):**
  - Columns: title, reporter, category, site, severity, status, priority, assignee, and created date.
  - Filters: status, severity, priority, category, site, assignee, a created date range, and free-text search (`q`). Sortable columns and pagination.
  - All filter, sort and page state lives in the URL search params.
  - A summary strip above the table shows counts of Open, In Progress and Critical-severity non-final incidents.
  - A Refresh button sits in the header.
- **`/incidents/[id]` (detail):**
  - Photo gallery.
  - A small Leaflet + OpenStreetMap map when `position` is present.
  - All fields, with reporter and site names resolved.
  - Triage panel:
    - A status select offering only the valid transitions.
    - A priority select and an assignee text field.
    - An append-only notes list with an "Add note" box.
  - Final incidents are read-only.

## 3. Android app (`android/`)

### 3.1 Foundations
- Package `com.example.hazardreporting`, **minSdk 26**, a single `:app` module.
- Packages: `domain`, `data`, `presentation`, `di`, `utils`. Dependencies are strict Clean ([ADR-0008](../../docs/adr/0008-strict-clean-with-model-grouped-interactors.md)).
- Libraries:
  - Dagger 2 (KSP)
  - Room (KSP)
  - Retrofit with the kotlinx.serialization converter
  - OkHttp with a logging interceptor (debug builds only)
  - DataStore Preferences
  - WorkManager
  - Navigation Compose (type-safe routes)
  - Core SplashScreen
  - Coil 3 with `coil-network-okhttp`
  - Play Services Location
  - Lifecycle runtime-compose
- Tests use JUnit4, MockK, Truth, Turbine and kotlinx-coroutines-test.
- `BASE_URL = "http://10.0.2.2:3001/"` is a constant beside the Retrofit builder. Cleartext is allowed only to `10.0.2.2` and `localhost`, through a debug `network_security_config`.
- The kotlinx `Json` is configured with `ignoreUnknownKeys = true`.
- Conventions:
  - KDoc on every class and public member, with `@author Roman Pliskin on <dd.MM.yyyy>`.
  - Threading and errors follow [ADR-0009](../../docs/adr/0009-coroutine-threading-and-error-conventions.md).
  - No `runCatching` in coroutine code.

### 3.2 Domain (`domain`)
- **Models:**
  - `IncidentSummary(localId, serverId?, title, categoryId, severityId, status, createdAt, syncState, hasStatusChangeNotice)`
  - `Incident(summary, details: IncidentDetails?)`
  - `IncidentDetails(description, siteId, locationDescription, position?, photos: List<Photo>, priority?)`
  - `Photo` is either a local file or a remote URL.
  - `IncidentDraft`: the fields a technician fills in on the form.
  - Enums `IncidentStatus` (Open, Acknowledged, InProgress, Resolved, Rejected, Withdrawn, Unknown), `Priority` (Low, Medium, High, Urgent, Unknown) and `SyncState` (Synced, PendingCreate, PendingUpdate, PendingWithdraw).
  - Catalog types `Category(id, name)`, `Severity(id, name, rank)`, `Site(id, name, lat, lng)`.
  - `User(id, email, name, role)` and `Position(lat, lng, accuracyM)`.
- **Repository interfaces:** `IncidentRepository`, `CatalogRepository`, `SessionRepository`, plus a `LocationProvider` interface.
- **Exceptions:** `NoConnectionException`, `InvalidCredentialsException`, `UnauthorizedException`, `ValidationException(fields: Set<Field>)`.
- **Interactors** are concrete classes, provided through `InteractorModule`:
  - `LoginInteractor`
    - `login(email, password)`
    - `logout(force: Boolean)`: tries to push pending changes. If some remain and `force` is false, it returns the pending count without wiping. Otherwise it runs the wipe.
    - `currentUser(): User?`
  - `CatalogInteractor`
    - `observeCategories()`, `observeSeverities()`, `observeSites()`
  - `IncidentInteractor`
    - `observeMyIncidents(): Flow<List<IncidentSummary>>`: excludes `PendingWithdraw` and `Withdrawn`, newest first.
    - `observeIncident(localId): Flow<Incident>`
    - `refreshIncidents()`: push pending changes, then pull the catalog and summaries.
    - `loadIncidentDetails(localId, force)`
    - `report(draft)`, `edit(localId, draft)`, `withdraw(localId)`, `dismissStatusChangeNotice(localId)`
  - Draft validation lives in `IncidentInteractor` and throws `ValidationException`:
    - title is 1–80 chars after trimming
    - description is at most 1000 chars
    - category, severity and site are all set
    - there are 1–3 photos

### 3.3 Data (`data`)
- **Room:**
  - `incidents`
    - `localId` (auto-increment primary key) and `serverId?`
    - the summary fields, plus `updatedAt`
    - the detail fields, all nullable, plus a `detailsLoaded` flag
    - `syncState`, `localVersion`, `createAttempted`, `statusChangeNoticePending`
  - `incident_photos`
    - `id`, `incidentLocalId` (foreign key with cascade delete), `position`, `localPath?`, `remoteUrl?`
  - `categories`, `severities`, `sites`
- **DataStore:** holds the session, `{ token, user }`.
- **Data sources:** `XxxLocalDataSource` (Room, DataStore, files) and `XxxRemoteDataSource` (Retrofit) are concrete classes. Remote data sources map `IOException` → `NoConnectionException` and `HttpException` 401 → `UnauthorizedException` (or `InvalidCredentialsException` on `/login`). Other exceptions propagate.
- **Converters:** DTO ↔ entity ↔ domain. Relative photo URLs are resolved against `BASE_URL`.
- **Detail loading:** fetch from the network when `force || !detailsLoaded`, then write to Room ([ADR-0006](../../docs/adr/0006-summaries-list-details-on-demand.md)).
- **Pull:** a pull must not overwrite the report fields of a row with a pending change. It updates only `status` and `updatedAt` there.
- **Session:** `SessionHolder` and `AuthInterceptor` behave as in [ADR-0010](../../docs/adr/0010-session-holder-blocking-fallback.md). The interceptor skips `/login`.
- **Location:** `LocationProvider`'s implementation uses `FusedLocationProviderClient.getCurrentLocation(PRIORITY_HIGH_ACCURACY)` with a 10 s timeout. If that fails, it falls back to `lastLocation` only when that fix is under 2 minutes old; otherwise it returns `null`.
- **Photo files:**
  - Camera output goes to app-private `files/photos/` through a `FileProvider`.
  - Gallery picks are copied there immediately.
  - Each local file is deleted once its upload succeeds.

### 3.4 Sync (`data/sync`)
See [ADR-0002](../../docs/adr/0002-offline-first-technician-app.md), [ADR-0003](../../docs/adr/0003-create-dedupe-by-reporter-and-created-at.md) and [ADR-0004](../../docs/adr/0004-field-owned-patch-and-open-only-edits.md).

`IncidentSynchronizer.push()` runs under a `Mutex`. For each pending row:
1. Upload every photo that has no `remoteUrl`, storing each URL as soon as it succeeds.
2. Send the request for the row's state:
   - `PendingCreate`: set `createAttempted = true`, then POST. Store the returned `serverId`.
   - `PendingUpdate`: PATCH the report fields.
   - `PendingWithdraw`:
     - If `!createAttempted`, delete the row and its files locally, and send nothing.
     - Otherwise, if there's no `serverId` yet, POST first.
     - Then PATCH `withdrawn`.
3. On success, mark the row `Synced` **only if `localVersion` is unchanged** since step 1 started. Otherwise leave it pending.
4. On **409**: drop the pending change, refetch the incident's details, overwrite the row, and set `statusChangeNoticePending = true`.
5. On `NoConnectionException`, stop and report "retry".
6. On `UnauthorizedException`, stop and expose a "session invalid" flag. The list shows it as a banner.

WorkManager:
- `SyncWorker` is created through a Dagger `WorkerFactory`. The default initializer is removed in the manifest.
- Unique one-shot work `sync-once` uses `ExistingWorkPolicy.KEEP`, a `NetworkType.CONNECTED` constraint and exponential backoff. It is enqueued after every `report`, `edit` and `withdraw`.
- Unique periodic work `sync-periodic` runs every 15 minutes and is push-only.

Logout wipe order ([ADR-0007](../../docs/adr/0007-logout-wipes-device-data.md)):
1. Cancel all work and acquire the sync `Mutex`.
2. Clear all Room tables.
3. Delete `files/photos/`.
4. Clear Coil's memory and disk caches.
5. Clear DataStore and `SessionHolder`.
6. Best-effort `POST /logout`.

### 3.5 Presentation (`presentation`)
- **Screen structure:** each screen is split into `XxxRoute(viewModel)` and a stateless `XxxScreen(state, onAction…)`. The ViewModel exposes one `StateFlow<XxxUiState>` and a `Flow<XxxEvent>`.
- **ViewModel coroutines:**
  - ViewModels launch with `viewModelScope.launch(exceptionHandler + dispatchers.default)`.
  - The shared handler logs through `Logger` and calls the ViewModel's `onUnexpected`, which clears loading state and shows a "Something went wrong" snackbar.
- **Look and feel:**
  - Material 3 with a fixed brand scheme (no dynamic colour), light and dark themes, and edge-to-edge.
  - All strings live in `strings.xml`, in English.
  - Every icon-only control has a content description.
- **Loading indicators:** no spinners except two:
  - the M3 pull-to-refresh indicator
  - the logout dialog
  
  Everything else uses the custom `Modifier.shimmer()` in `presentation/common`.
- **Navigation:**
  - Type-safe routes: `Login`, `IncidentList`, `IncidentDetail(localId: Long)` and `IncidentForm(localId: Long? = null)`.
  - The splash screen stays up until `currentUser()` decides the start destination.
- **Colours:**
  - Severity by rank: Low is neutral, Medium amber, High orange, Critical uses `error`.
  - Status chips use tonal colours:

    | Status | Colour |
    |---|---|
    | Open | primary container |
    | Acknowledged | secondary container |
    | In Progress | tertiary container |
    | Resolved | muted green |
    | Rejected | outline |

#### Login
- Email and password fields. The IME action on the password field submits.
- While a request is in flight:
  - the button keeps its enabled look but ignores taps
  - its container shimmers and its label reads "Signing in…"
  - the fields are disabled
- Errors show as inline text under the password field: "Invalid email or password" or "No connection".
- On success, navigate to `IncidentList` with the back stack cleared, and trigger `refreshIncidents()`.

#### Incident list
- **Top bar:** title "My incidents", with a ⋮ menu containing Log out.
- **Rows:** title (1 line), "Category · Site" (1 line), a severity chip, a status chip and the created date. A cloud-upload icon shows when the row is pending, and a warning icon when it has a Status Change Notice.
- **Extended FAB:** "Report incident", which collapses to just the icon while scrolling.
- **States:**

  | State | What shows |
  |---|---|
  | First load | 6 shimmering skeleton rows |
  | Empty | "No incidents reported yet" with a hint pointing at the FAB |
  | First-load failure | An inline error card with Retry |
  | Refresh failure, data shown | The data stays, plus the snackbar "Couldn't refresh — showing saved data" |
  | Session invalid | A persistent banner: "Session no longer valid — log out and sign in again to sync." |

- **Pull-to-refresh:** calls `refreshIncidents()`.
- **Saved result:** when a "saved" result arrives from the form through the previous back-stack entry's `SavedStateHandle`, the snackbar "Report saved" shows.
- **Logout:**
  1. The dialog asks "Log out? Data on this device will be removed."
  2. On confirm, it shows a spinner and "Sending N pending reports…" with its buttons disabled.
  3. If everything was sent, the app wipes and navigates to `Login` with the back stack cleared.
  4. If anything is still unsent, the dialog says "N reports couldn't be sent and will be lost", with **Log out anyway** and **Cancel**.

#### Incident detail
- Opening the screen calls `loadIncidentDetails(localId, force = false)`, and pull-to-refresh calls it with `force = true`.
- **Photos:** a `HorizontalPager` with a page indicator. Each image shimmers while it loads.
- **Fields:** title, status and severity chips, priority (shown as "—" when unset), category, site, location description, position ("±12 m" plus coordinates) and the created date as an absolute local date and time. There is **no assignee**.
- **Details not loaded yet:** the detail fields shimmer. If loading fails, they are replaced by "Details not downloaded" with a Retry button.
- **⋮ menu (Edit, Withdraw…):** shown only when details are loaded and the status is Open. Withdraw asks for confirmation: "Withdraw this report? Operators will no longer act on it." After withdrawing, the app navigates back.
- **Pending indicator:** while the row has a pending change, the screen shows "Waiting to send".
- **Status Change Notice:** a banner reading "Status changed to <status> by an operator — your changes were not applied". It appears live if the notice arrives while the screen is open. Dismissing it calls `dismissStatusChangeNotice`.

#### Report / edit form
- **Top bar:** "New report" or "Edit report", with ✕ to close and a **Save** text action.
- **Photos come first:**
  - A strip of up to 3 thumbnails, each with a remove ✕.
  - An "Add photo" tile opens a bottom sheet with Camera (the `TakePicture` contract) and Gallery (`PickVisualMedia`).
- **Then, in order:**
  1. Title
  2. Description
  3. Category (exposed dropdown)
  4. Severity (4 segmented buttons, coloured by rank)
  5. Site (exposed dropdown)
  6. Location description
  7. A read-only position line with a Re-capture button
- **Position:**
  - In create mode, it's captured once when the form opens, after requesting fine and coarse location permission. Approximate-only permission is accepted.
  - If permission is denied or no fix is available, the report is saved without a position.
  - In edit mode, the original position is kept.
- **Process death:** form state and the pending camera `Uri` are kept in `SavedStateHandle`, so they survive.
- **Validation:** errors show inline only after the first Save attempt or once a field has lost focus. The rules live only in the interactor.
- **Back or ✕ with unsaved changes:** a "Discard changes?" dialog.
- **Save:** instant, with no busy state. It goes back and passes a "saved" result to the previous screen.

## Acceptance (end-to-end demo)

1. `npm run reset && npm run dev` in `server/`, `npm run dev` in `dashboard/`, and the app runs on an emulator.
2. tech1 logs in and sees only their seeded incidents. Withdrawn ones are hidden.
3. With the emulator in airplane mode, tech1 reports an incident with 2 photos. It appears with a pending icon. Then connectivity comes back, and within a minute it is synced and visible on the dashboard. There is exactly one copy even if the connection dropped mid-POST.
4. ops acknowledges that incident on the dashboard. tech1 edits it offline from a stale detail screen. On sync the edit is refused, the incident shows Acknowledged, and a Status Change Notice appears.
5. tech1 withdraws an Open incident. It disappears from the app and shows as Withdrawn on the dashboard.
6. ops filters by severity Critical and status Open, resolves an incident, and adds a note. tech1 refreshes and sees Resolved, but never the note or the assignee.
7. tech1 logs out while offline with a pending report. The app warns "1 report … will be lost" before wiping.
